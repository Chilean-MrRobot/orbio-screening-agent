# 013 — CRM para recruiters, con analítica

**Estado:** implementada
**Ola:** 3 · **Depende de:** 000, 001, 008

## Objetivo
Darle a los recruiters de Grupo Sazón una herramienta para seguir a los candidatos en vivo
y ver "la magia que ocurre": la conversación, lo que el agente extrajo, por qué un
candidato califica o queda fuera, cuánto puntaje saca y cuánto cuesta. Además, una
analítica de las conversaciones para medir el embudo.

## Alcance
- Incluye:
  - Un router de la API (`/crm/...`) protegido con un token (`CRM_API_TOKEN`): listado con
    filtros, ficha completa, cambio de estado manual y métricas.
  - Una función pura de analítica sobre la lista de fichas.
  - Una app de Streamlit que lee la API por HTTP, con contraseña simple (`CRM_PASSWORD`).
  - Un agente guionado de demo y `scripts/seed_demo.py`, que llena la API local con
    12 candidatos pasando por el flujo real, sin gastar en LLM.
  - Guía para correr el CRM en local y desplegarlo en Cloud Run.
- No incluye:
  - Usuarios, roles ni login real (una contraseña compartida basta para el demo).
  - Edición de los datos de la ficha desde el CRM, notas libres o agendar entrevistas.
  - Paginación: el demo maneja decenas de fichas; la API devuelve todas y filtra en memoria.
  - Cancelar los toques de calentamiento al mover el estado: la spec 011 decide qué
    estados reciben toques.

## Interfaz

### API (`screening.api.crm`)
`build_crm_router(repository, clock, token) -> APIRouter`. Todas las rutas exigen
`Authorization: Bearer <CRM_API_TOKEN>`; sin token o con uno distinto, `401`.
`create_app_from_env` monta el router solo si `CRM_API_TOKEN` está definido. Así el
cambio en `app.py` se reduce a aceptar un router opcional e incluirlo.

| Método y ruta | Entrada | Salida |
|---|---|---|
| `GET /crm/candidates` | `status` (repetible), `country`, `stage` | `list[CandidateRow]` |
| `GET /crm/candidates/{id}` | — | `Candidate` (ficha completa) o `404` |
| `POST /crm/candidates/{id}/status` | `StatusChangeRequest` | `Candidate` actualizado, `404`, `409` o `422` |
| `GET /crm/metrics` | `stale_hours` (opcional, por defecto 24) | `CrmMetrics` |

Las rutas viven bajo `/crm` para no chocar con `/applications` ni el webhook.

### Listado (`screening.crm.listing`)
```python
class LastMessage(BaseModel):
    role: MessageRole
    text: str
    at: datetime

class CandidateRow(BaseModel):
    id: str
    name: str | None            # data.full_name o, si falta, el de la postulación
    phone: str | None
    country: Country | None
    city: str | None            # data.city o, si falta, el de la postulación
    status: CandidateStatus
    stage: Stage
    score: float | None
    disqualification_reason: str | None
    human_requested: bool
    sentiment: Sentiment
    needs_review: list[str]
    last_message: LastMessage | None
    created_at: datetime
    updated_at: datetime

def to_row(candidate: Candidate) -> CandidateRow
def filter_and_sort(candidates, *, statuses=None, country=None, stage=None) -> list[Candidate]
```
Orden: puntaje descendente (sin puntaje al final) y, a igual puntaje, la actividad más
reciente (`updated_at`) primero.

### Transiciones manuales (`screening.crm.transitions`)
```python
class StatusChangeRequest(BaseModel):
    status: Literal["interview", "hired", "disqualified"]
    reason: str | None = None     # obligatorio (no vacío) para "disqualified"
    recruiter: str | None = None

def allowed_targets(status: CandidateStatus) -> list[CandidateStatus]
def apply_status_change(candidate, request, now) -> None   # lanza TransitionError
```

| Destino | Desde |
|---|---|
| `interview` | `qualified`, `in_screening`, `contacted`, `no_response`, `invalid_data` |
| `hired` | `interview` |
| `disqualified` | cualquiera salvo `disqualified`, `opted_out` y `hired` |

`interview` también se permite desde estados abiertos para el caso del candidato que pidió
hablar con una persona o que el recruiter quiere adelantar.

Al aplicar: `set_status(destino, now, reason=...)`, `set_stage(done, now)` (la conversación
automática termina) y un evento `recruiter_action` con `status`, `reason` y `recruiter`.

### Analítica (`screening.crm.metrics`)
`compute_metrics(candidates: list[Candidate], now: datetime, stale_after: timedelta) -> CrmMetrics`

```python
class TokenMetrics(BaseModel):
    calls: int
    input_tokens: int
    output_tokens: int
    total_cost_usd: float
    avg_cost_per_candidate_usd: float | None  # sobre fichas con al menos una llamada
    cost_per_qualified_usd: float | None  # costo total / calificados


class CrmMetrics(BaseModel):
    total: int
    by_status: dict[CandidateStatus, int]  # todos los estados, con ceros
    by_country: dict[str, int]  # "ES", "MX" o "unknown"
    contacted: int
    responded: int
    completed: int
    qualified: int
    response_rate: float | None  # responded / contacted
    completion_rate: float | None  # completed / responded
    qualification_rate: float | None  # qualified / completed
    drop_off_by_stage: dict[Stage, int]
    disqualification_reasons: dict[str, int]
    avg_minutes_to_qualify: float | None
    reengagement_touches: int
    candidates_reengaged: int
    human_requested: int
    avg_score: float | None
    tokens: TokenMetrics
```

### Cliente HTTP (`screening.crm.client`)
`CrmClient(base_url, token, *, transport=None, timeout=10)` con `list_candidates`,
`get_candidate`, `change_status` y `metrics`, que devuelven los modelos de arriba ya
validados. Un error HTTP se convierte en `CrmApiError(status_code, detail)`.
`CrmClient.from_env()` lee `CRM_API_URL` y `CRM_API_TOKEN`.

### App (`screening.crm.app`) y vistas (`screening.crm.views`)
La app solo dibuja; la lógica de datos (etiquetas, registros de la tabla, filas del
`timeline`, burbujas del chat, formato de duraciones) vive en `views.py` y se testea.

### Demo (`screening.crm.demo` y `scripts/seed_demo.py`)
- `DemoAgent`: `ScreeningAgent` guionado. Busca cada mensaje del candidato en una tabla de
  extracciones conocidas y responde con preguntas fijas por campo. Registra un uso de
  tokens estimado (≈ 4 caracteres por token, precio de `config/llm_pricing.yaml`) para que
  la analítica de costo tenga datos.
- `DEMO_SCENARIOS`: 12 candidatos (ES y MX) con sus mensajes y acciones del recruiter.
- `create_demo_app()`: la API con el `DemoAgent` y el canal de consola (nunca WhatsApp).
- `scripts/seed_demo.py`: con la API de demo corriendo, envía cada postulación a
  `POST /applications`, cada mensaje firmado al webhook de WhatsApp y las acciones del
  recruiter a la API del CRM; espera la respuesta de cada mensaje antes del siguiente.

## Comportamiento
- **Fuente de datos:** el CRM nunca lee la base directo; el repositorio en memoria vive en
  el proceso de la API.
- **Tiempo real:** la tabla y la ficha abierta se refrescan cada pocos segundos
  (`st.fragment(run_every=...)`), sin recargar la página.
- **Filtros:** `status` acepta varios valores; `country` y `stage` uno. Un valor fuera del
  enum responde `422`.
- **Cambio de estado:** destino no permitido desde el estado actual → `409` con el motivo;
  descarte sin motivo → `422`; destino distinto de los tres manuales (por ejemplo
  `qualified`) → `422`.
- **Métricas** (todas sobre las fichas recibidas):
  - *Contactado:* la ficha tiene al menos un mensaje del agente. *Respondió:* al menos un
    mensaje del candidato. *Completó:* llegó a un veredicto (`qualified`, `disqualified`,
    `interview` o `hired`). *Calificado:* `qualified`, `interview` o `hired`.
  - *Abandono por etapa:* fichas en `no_response` u `opted_out`, más las de `contacted` o
    `in_screening` sin actividad (`updated_at`) en `stale_after`; se cuentan por `stage`.
  - *Motivos de descarte:* `knockout.reason_code` si una regla falló; si no, `manual`
    (descarte del recruiter).
  - *Duración hasta calificar:* de `created_at` al primer evento `status_changed` a
    `qualified`; promedio en minutos.
  - *Calentamiento:* suma de `reengagement.touches_sent` y cuántas fichas recibieron al
    menos un toque.
  - *Tokens:* suma de los eventos `llm_usage` del `timeline` (`usage_totals`, spec 008).
  - Las tasas con denominador cero son `None`, no `0`.
- **Contraseña de la app:** se compara con `hmac.compare_digest`; sin `CRM_PASSWORD`
  definida, la app no arranca (muestra un error).

## Criterios de aceptación
- **Dado** `CRM_API_TOKEN`, **cuando** se llama a cualquier ruta del CRM sin token o con uno
  incorrecto, **entonces** responde `401`.
- **Dado** fichas con y sin puntaje, **cuando** se pide `GET /crm/candidates`, **entonces**
  vienen por puntaje descendente, las sin puntaje al final y empates por actividad reciente.
- **Dado** filtros `status=qualified&status=interview&country=MX`, **cuando** se lista,
  **entonces** solo vienen fichas de México en esos estados.
- **Dada** una ficha `qualified`, **cuando** el recruiter la mueve a `interview`, **entonces**
  queda en `interview`, etapa `done`, con `status_changed` y `recruiter_action` en el
  `timeline`, y se guarda.
- **Dada** una ficha `qualified`, **cuando** se pide `hired`, **entonces** `409` y la ficha
  no cambia.
- **Cuando** se descarta sin motivo, **entonces** `422`.
- **Dada** una lista de fichas armadas a mano, **cuando** se calculan las métricas,
  **entonces** cada número coincide con la definición de arriba.
- **Dado** el cliente con un transporte falso, **cuando** la API responde `401`, **entonces**
  lanza `CrmApiError` con el código.
- **Dados** los 12 escenarios de demo, **cuando** pasan por el orquestador con el
  `DemoAgent`, **entonces** cada uno termina en el estado esperado.

## Tests
- `tests/unit/crm/test_api.py`: rutas con y sin token, `404`, filtros y orden, cambio de
  estado válido e inválido (`409`, `422`), métricas por HTTP y que `create_app` sin router
  del CRM no expone las rutas.
- `tests/unit/crm/test_metrics.py`: cada métrica con fichas armadas en el test, incluidas
  la lista vacía y las tasas con denominador cero.
- `tests/unit/crm/test_listing.py` y `test_transitions.py`: filas, filtros, orden y matriz
  de transiciones.
- `tests/unit/crm/test_client.py`: el cliente con `httpx.MockTransport` (cabecera, filtros,
  parseo y errores).
- `tests/unit/crm/test_views.py`: la lógica de datos de la UI.
- `tests/unit/crm/test_demo.py`: los escenarios de demo terminan en el estado esperado.
